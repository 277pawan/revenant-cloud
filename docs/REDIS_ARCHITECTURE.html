Self-hosted Redis · no AWS

Proving a Redis backup actually restores

A cache keeps its RDB on the same disk that fails, and nobody checks whether that file still loads. Revenant takes a real snapshot off a live Redis, boots a throwaway server against that exact file, and reports what came back.

Why the sandbox runs with persistence off

The restored server is booted with --save "" --appendonly no and a read-only mount of the scratch directory. It physically cannot write back into your dump, and it cannot leave a second file behind.

Why nothing expensive runs on the live cache

A proof must never stall production traffic. Source-side numbers come only from INFO keyspace, which is O(number of databases). No SCAN, no Lua, no O(N) walk against your real Redis.

Connecting

From a pasted URL to a running proof

Four steps, and the first one saves nothing.

  1. Paste and test

    redis://:password@host:6379/0 or rediss:// for TLS. Nothing is stored. The API opens a connection, PINGs, and returns a fingerprint. An unreachable Redis is a valid answer, not a failure — it comes back amber with "use the CLI or the agent", because a private-network Redis is the expected case.

  2. Register it

    The URL is encrypted with AES-256-GCM and written to redis_credentials. It is never returned by any endpoint, never logged, and requirepass is recorded only as SET or NOT SET — the value itself is discarded.

  3. Choose whether to keep anything

    Off by default. With storage off, Revenant verifies and keeps nothing. With it on, each artifact gets a mandatory TTL that the API clamps down to your plan — ask for a year on Starter, get 24 hours.

  4. Run a proof

    Click Run. A redis_proofs row goes to pending and your monthly quota is counted. An agent claims it, does the work, and reports back. If no agent exists, the row simply waits — it never silently burns quota.

Snapshot & restore

How a snapshot is captured and proven

The whole point is that checks run against the restored instance, not the live one.

  1. Claim

    Two indexed queries with FOR UPDATE … SKIP LOCKED. Concurrent agents never collide. Idle cost is an index-only scan of a near-empty partial index.

  2. Pull the dump — without touching your disk

    redis-cli --rdb dump.rdb asks the server to stream a complete RDB over the wire. No filesystem access, no local redis-cli needed, and it works when Redis lives in a container or a volume.

  3. Boot a throwaway server against that copy

    The dump is copied to a scratch dir, a random loopback port is bound, and the sandbox is started with persistence disabled. Revenant waits for it to answer PING rather than assuming success — a large RDB takes real time to load.

  4. Check the restored instance

    DBSIZE, keyspace counts, config posture, and a keyspace digest — all against the copy. Source key counts come from INFO keyspace and are compared.

  5. Compare, honestly

    An exact key-count match is not required — keys legitimately expire between capture and restore. A small shortfall passes; 50% or more is reported as a failure with "check your save policy", because that usually means a stale dump.

What a large key shortfall usually means: the RDB is stale, not corrupt. Redis's default save 3600 1 only snapshots once an hour and only after a write. A cache that went quiet for two hours has a dump that is two hours old — and this is exactly the failure the product exists to surface.
Compression

Measured, because the first assumption was wrong

An earlier draft claimed an RDB is "already LZF-compressed, so re-compressing buys only 5–15%". That was measured, and it was wrong. LZF trades ratio for BGSAVE speed and leaves a lot behind.

72.8% smaller with gzip — 40k mixed cache keys, RDB 2,900,435 B → 788,756 B
86.9% smaller with gzip — 20k JSON product docs, RDB 2,089,173 B → 274,129 B

All three round-trip byte-identical through the shipped code. gunzip runs at ~322 MB/s single-core, so decompression is noise in a restore — which is why gzip is the default, and zstd is opt-in on Node ≥ 22.15.

The encoding is recorded per artifact in redis_snapshots.compression, and the file extension is derived from it. Changing the setting later can never break restoring an older snapshot — the row always knows how it was actually written.
Retention

The TTL is the feature

An unbounded snapshot in our bucket is an unbounded bill and an unbounded data-protection obligation. There is no code path that produces one.

Three independent guards

Schema
expires_at NOT NULL — no deadline, no row.
Constraint
A CHECK rejects an enabled resource with no positive retention window, at the database level.
Clamp
resolveRedisSnapshotRetentionHours() clamps down to the plan ceiling. 8760 requested → 24 granted.
Sweeper
Every 5 minutes, expired artifacts are hard-deleted — the bytes, not just the row.
